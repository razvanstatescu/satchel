# C1 · C2 · C3 · C7: history digest, USDC on EVM, more EVM testnets, message signing

Owner: `contract-sign` (branch `feat/contract-sign`). Status: **interface fixed 2026-10-29**; the phase-2 UIs build
against this file. It extends kb/90 §5 (contract) and §7 (clean history), and wins over them where they differ for
these four features. Everything not named here is unchanged: `sign_for`'s signature, its guard order (owner, frozen,
count, gas, mpc deposit), the record-before-MPC rule, the `on_signed` contract, events other than the additions below.

Encoding rules are kb/90 §5.3's: bytes are lowercase hex without `0x` in outputs (inputs accept `0x` and either case),
token amounts are decimal strings, counters are JSON numbers, enum tags are snake_case.

---

## 3. Request kinds (`sign_for(token_id, request, mpc_deposit)`, signature unchanged)

`SignRequest` is externally tagged. Two variants are added **at the end**; the three existing ones are unchanged.

```jsonc
{"evm":{"unsigned_tx":"02f86d…c0"}}                     // C2 + C3: type-2 tx on any chain of §2 (native, or USDC transfer)
{"btc":{"preimages":["…"],"outputs":"…"}}               // unchanged
{"sol":{"message":"01000103…"}}                         // unchanged
{"evm_message":{"message":"5369676e20696e20746f…"}}     // C7: hex of the UTF-8 message body (NOT prefixed)
{"sol_message":{"message":"5369676e20696e20746f…"}}     // C7: hex of the UTF-8 message body (NOT the off-chain header)
```

Each produces exactly one record and one MPC request (n = 1), so gas is unchanged: attach `80 Tgas` (floor 48).

### 3.1 EVM transaction rules (`parse/evm.rs`, replaces the kb/90 §5.9 EVM table)

Layout unchanged: `0x02 ‖ rlp([chain_id, nonce, tip, max_fee, gas_limit, to, value, data, access_list])`.
Checks run in this order; the first failure is the error.

| # | Rule | Error |
|---|---|---|
| 1 | `len ≤ 160` (was 128; a maximal USDC transfer is 152 B, a maximal native one 99 B) | `ERR_EVM_TOO_LONG` |
| 2 | `p[0] == 0x02` | `ERR_EVM_TYPE` |
| 3 | canonical RLP, one 9-item list consuming every byte, minimal ints, depth ≤ 16, items 0–7 byte strings, item 8 a list | `ERR_EVM_RLP` |
| 4 | `chain_id` ≤ 8 bytes and ∈ {11155111, 84532, 421614, 11155420} | `ERR_EVM_CHAIN_ID` |
| 5 | `nonce`, `gas_limit` ≤ 8 bytes; `nonce < 2^64 − 1`; `tip`, `max_fee`, `value` ≤ 16 bytes | `ERR_EVM_INT_WIDTH` |
| 6 | `to` is exactly 20 bytes | `ERR_EVM_TO` |
| 7 | `data` is empty, **or** exactly 68 bytes = `a9059cbb` ‖ 12 zero bytes ‖ 20-byte recipient ‖ 16 zero bytes ‖ 16-byte amount (a canonical `transfer(address,uint256)` with the address zero-padded and the amount `< 2^128`) | `ERR_EVM_DATA` |
| 8 | if `data` is a transfer: `to` is the USDC of **this tx's** `chain_id` (§2) | `ERR_EVM_TOKEN` |
| 9 | if `data` is a transfer: `value == 0` | `ERR_EVM_VALUE` |
| 10 | `access_list` is empty | `ERR_EVM_ACCESS_LIST` |
| 11 | **nonce-gap rule, per chain** (state; after every rule above, before any write): with `m` = the highest nonce of this token's EVM records **on this `chain_id`**, require `nonce ≤ m + 1`, or `nonce ≤ 1` when the token has no EVM record on that chain | `ERR_EVM_NONCE_GAP` |

Notes:
- A transfer amount of 0 and any recipient (including the token itself) are accepted: at worst they revert and use
  up the nonce, which the clean-history nonce rule already treats as spent.
- Message records (§3.3) never touch EVM nonces.
- Clean history needs no new rule for C2: a USDC transfer is dead once its nonce is used, like any EVM tx.

### 3.2 Per-chain nonce state (C3)

- **Sepolia (11155111)** keeps using `TokenState.max_evm_nonce` (unchanged layout, unchanged charge).
- **The other three chains** use a new map in its own module (`contracts/satchel/src/evm_nonces.rs`):
  `LookupMap<(TokenId, u64 /* chain_id */), u64 /* max signed nonce */>` under `StorageKey::EvmNonces`, **appended**
  to the enum. It is not a field of `Contract` (the map is opened on demand), so the root state layout is unchanged.
- The first record on a new (token, chain) writes ≈ 63 B (0.00063 NEAR), charged to the requester inside `sign_for`'s
  exact storage charge. Updates after that are in place (no growth).
- The state belongs to the token: it survives transfers and sales, like the records.

### 3.3 Message rules (C7, `parse/msg.rs`)

| # | Rule | Error |
|---|---|---|
| 1 | strict hex | `ERR_HEX` |
| 2 | `1 ≤ len(message) ≤ 1024` bytes | `ERR_MSG_EMPTY` / `ERR_MSG_TOO_LONG` |
| 3 | the message is valid UTF-8 | `ERR_MSG_ENCODING` |

**What gets signed** (built by the contract, never by the caller):

- `evm_message` (EIP-191 version `0x45`, i.e. `personal_sign`): `bytes = "\x19Ethereum Signed Message:\n" ‖ ascii_decimal(len) ‖ message`.
  MPC payload `Ecdsa(hex(keccak256(bytes)))`, domain 0, path `satchel/{id}/evm`. Record payload = `keccak256(bytes)`.
  Any EIP-191 verifier (`viem.verifyMessage`, `ethers.verifyMessage`, `ecrecover(toEthSignedMessageHash(m))`) accepts
  the signature with `v = 27 + recovery_id`.
- `sol_message` (Solana off-chain message **v0**, as `solana-sdk`'s `OffchainMessage` and `solana sign-offchain-message`
  build it): `bytes = "\xffsolana offchain" (16 B) ‖ 0x00 (version) ‖ format ‖ u16le(len) ‖ message`, with
  `format = 0` (restricted ASCII) if every byte is in `0x20..=0x7e`, else `1` (limited UTF-8).
  MPC payload `Eddsa(hex(bytes))` (≤ 1044 B), domain 1, path `satchel/{id}/sol`. Record payload = `sha256(bytes)`.
  The first byte `0xff` can never start a Solana transaction message (legacy messages start below `0x80`, versioned
  ones at `0x80 | version` and `0xff` is not a valid version), so this signature can never be a transaction signature.

**Refused on purpose:** EIP-712 typed data (permits, Permit2, EIP-3009, orders), raw 32-byte hashes, `eth_sign`,
Solana raw `signMessage` bytes (they could be a transaction), the newer Solana off-chain format with an application
domain and a signer list, and BIP-322 (§9).

### 3.4 Why a message signature can't move the coins a buyer checks

- **ETH:** only a transaction moves ETH. A transaction hash is `keccak(0x02 ‖ …)` and a 7702 authorization is
  `keccak(0x05 ‖ …)`; a message hash is `keccak(0x19 0x45 ‖ …)`. Different first bytes, so no message signature is ever
  valid for either.
- **USDC:** it moves by the holder's transaction, by `transferFrom` under an allowance, or by an EIP-2612 permit /
  EIP-3009 authorization. The contract never signs `approve` (§3.1 rule 7), and permits and authorizations are EIP-712
  digests (`keccak(0x19 0x01 ‖ …)`), a different prefix again.
- **SOL:** an off-chain message can never parse as a transaction (above).
- **What a message can do:** whatever an off-chain service decides it means: a log-in, a proof of ownership, an
  account at a dapp that holds its own balances keyed to this address. Those are outside what the checker verifies
  and what a buyer pays for. The checker therefore lists every message, with its full text, without blocking (§7).

## 4. Records

### 4.1 Stored (`SigDetail`, borsh; two variants **appended**, so existing records keep their tags)

```rust
pub enum SigDetail {
    Evm { chain_id: u64, nonce: u64, unsigned_tx: Vec<u8> },   // tag 0, now also ERC-20 and the 3 new chains
    Btc { txid: [u8; 32], vout: u32, amount_sats: u64 },        // tag 1, unchanged
    Sol { recent_blockhash: [u8; 32], lamports: u64 },          // tag 2, unchanged
    EvmMessage { message: Vec<u8> },                            // tag 3, C7: the body, ≤ 1024 B
    SolMessage { message: Vec<u8> },                            // tag 4, C7: the body, ≤ 1024 B
}
```

ERC-20 fields are **not stored separately**: they are inside `unsigned_tx`, which is the exact byte string the contract
classified, and the view derives them from it.

### 4.2 `sig_records` rows (`SigRecordView`, other fields unchanged)

```jsonc
// native transfer, any chain of §2
{"seq":0,"chain":"evm","detail":{"evm":{"chain_id":84532,"nonce":0,"unsigned_tx":"02…"}}, "…":"…"}
// USDC transfer: same tag, plus "erc20" (absent on native transfers, never null)
{"seq":1,"chain":"evm","detail":{"evm":{"chain_id":11155111,"nonce":1,"unsigned_tx":"02f86d…",
   "erc20":{"token":"1c7d4b196cb0c7b01d743fbc6116a902379c7238","to":"61739f33adbb7f76c1b5b222e4119085257528be","amount":"1500000"}}}, "…":"…"}
// EIP-191 message: chain "evm" (the EVM key signed it)
{"seq":2,"chain":"evm","payload":"<keccak256 of the prefixed bytes>","signature":{"r":"…","s":"…","recovery_id":0},
 "detail":{"evm_message":{"message":"5369676e20696e"}}, "…":"…"}
// Solana off-chain message: chain "sol"
{"seq":3,"chain":"sol","payload":"<sha256 of the off-chain bytes>","signature":{"signature":"<64 B hex>"},
 "detail":{"sol_message":{"message":"5369676e20696e"}}, "…":"…"}
```

- `erc20.amount` is a decimal string in token base units (USDC: 6 decimals). `token` and `to` are 20-byte hex.
- Message bodies are hex of the exact UTF-8 bytes. Decode with `TextDecoder('utf-8', {fatal: true})`; the contract
  guarantees it succeeds.
- A client must still check `keccak256(unsigned_tx) == payload` (EVM tx), `keccak256(eip191(message)) == payload`
  and `sha256(offchain(message)) == payload` (messages). `@satchel/core` does this.

### 4.3 `sign_requested` event (`details[i]`, other fields unchanged)

```jsonc
{"seq":0,"chain_id":84532,"nonce":0}                                                   // native (unchanged shape)
{"seq":1,"chain_id":11155111,"nonce":1,"erc20":{"token":"1c7d…7238","to":"6173…28be","amount":"1500000"}}
{"seq":2,"kind":"evm_message"}      // preimages[0] = the full prefixed bytes; payloads[0] = their keccak256
{"seq":3,"kind":"sol_message"}      // preimages[0] = the full off-chain bytes (also the MPC Eddsa payload)
```

INV-08 holds for every kind: each `preimages[i]` hashes (keccak for EVM, sha256 for SOL) to `payloads[i]`.

### 4.4 Storage cost per record

| Kind | ≈ bytes | ≈ NEAR | What callers attach |
|---|---|---|---|
| EVM native | 280 | 0.0028 | 0.005 NEAR (unchanged) |
| EVM USDC transfer | 350 | 0.0035 | 0.005 NEAR |
| first record on a new chain (§3.2) | + 63 | + 0.00063 | included in 0.005 NEAR |
| message of `L` bytes | 215 + L | 0.00215 + L × 0.00001 | `0.005 NEAR + L × 0.00001 NEAR` (`messageSignAttachDeposit(L)`, ≤ 0.01524 NEAR) |

The contract charges the measured bytes exactly and refunds the excess (INV-18, unchanged).

## 5. Views

### 5.1 `history_digest(token_id) -> Option<HistoryDigestView>` (C1)

```jsonc
history_digest("3") → {"sig_count":4,"digest_hex":"9f2c…e1"}       // null if the token doesn't exist
```

`digest_hex` = lowercase hex of

```
SHA-256( H ‖ E(r_0) ‖ E(r_1) ‖ … ‖ E(r_{n−1}) )         n = sig_count, records in seq order
```

Everything is **borsh** (u8/u32/u64 little-endian; `str(x)` and `bytes(x)` = `u32le(len) ‖ raw`; arrays raw):

```
H    = str("satchel.history.v1") ‖ str(contract_account_id) ‖ str(token_id) ‖ u64(n)
E(r) = u64(seq) ‖ u64(request_id) ‖ u8(input_index) ‖ u64(height) ‖ u64(timestamp_ms) ‖ str(requester)
       ‖ payload[32] ‖ D(detail)
D    = 0x00 ‖ u64(chain_id) ‖ u64(nonce) ‖ bytes(unsigned_tx)              Evm
     | 0x01 ‖ txid[32] (display order, as in the view) ‖ u32(vout) ‖ u64(amount_sats)   Btc
     | 0x02 ‖ recent_blockhash[32] ‖ u64(lamports)                         Sol
     | 0x03 ‖ bytes(message)                                               EvmMessage
     | 0x04 ‖ bytes(message)                                               SolMessage
```

- **Only immutable fields.** `status` and `signature` are excluded: `on_signed` rewrites them after the request, and
  a late callback may even land while listed (review S-10). Two reads of the same history therefore always agree.
- `H` binds the contract account and token id, so an rc digest never matches a final one, and the count makes the
  encoding unambiguous. For `sig_count == 0` the digest is `SHA-256(H)`.
- **Recompute it off-chain** from `sig_records` pages with `historyDigest(contractId, tokenId, records)` in
  `@satchel/core/clean-history`, and compare: equal digests mean equal histories. Shared vector:
  `vectors/history.json` (Rust and TS both reproduce it; the sandbox suite checks a third, independent implementation).
- **Cost (measured, review L-03).** The view reads and hashes every record. Measured on the sandbox
  (`tests/tests/review.rs::sr05_history_digest_gas_ceiling`, wasm `bd5d8e01…`) as a 300 Tgas call: ≈ 0.092 Tgas per
  small record (a native EVM tx), so 3,000 records fit (276 Tgas) and 4,000 don't; ≈ 0.133 Tgas per 1,024-byte
  message record (C7), so 2,000 fit (266 Tgas) and 2,500 don't. A marketplace contract can call it cross-contract to
  bind an order to `(sig_count, digest)` without reading the records itself, but a cross-contract call gets less than
  300 Tgas, so budget about **1,500 records** for a message-heavy history. Beyond that, page `sig_records` and hash
  client-side with `historyDigest` (same result).

### 5.2 `max_evm_nonce(token_id, chain_id) -> Option<u64>` (C3)

The highest nonce this token ever signed on `chain_id` (any status), or `null` if none (or an unsupported chain). The
next request on that chain may use at most `max + 1` (or 1 when `null`). Clients may also compute it from
`sig_records` (`maxSignedEvmNonce(records, chainId)`); both must agree.

## 7. Clean history (kb/90 §7, additions)

### 7.1 EVM, per chain (C3)
- The checker groups EVM transaction records by `detail.evm.chain_id` and runs the §7.2 nonce rule **separately for
  each chain**, on that chain's providers: `eth_chainId` guard, then the nonce counts at `latest − 3` and `latest` on
  **two providers that must agree** (both read at the same block number, min head − 3). Statuses are the existing
  ones: `spent`, `settling`, `unused`, `unknown`.
- `eth_getCode(address) == "0x"` is checked on Sepolia always and on every other chain that has records; any code
  (e.g. an EIP-7702 marker) makes the token `unsafe`. Account reports carry `chain_id`.
- A supported chain with no configured providers, or with both down, gives `unknown` (blocks Buy). A `chain_id`
  outside §2 gives `unknown` / `chain_unsupported`.
- USDC transfer records follow the same nonce rule; the item report adds `erc20 {token, to, amount}`.

### 7.2 Message records (C7)
- New item status **`message`** (reason `message_signature`), **never blocking**. The aggregate is `clean` when every
  item is `spent`, `expired`, `unfunded`, `foreign` or `message`.
- The item report carries `message_kind` (`evm_message` / `sol_message`) and `message_text` (the decoded UTF-8), so
  the Buy tab can list them: "Signed a message: '…'. Messages can't move coins."
- A record whose payload doesn't match its message (`keccak256(eip191(m))` / `sha256(offchain(m))`) is `unknown` /
  `record_inconsistent` (fail closed; it can't happen with a correct NEAR source).
- A pre-C7 checker sees `evm_message`/`sol_message` details as unparseable and returns `unknown`: old app versions fail
  closed.

### 7.3 Verified balance (C2)
- The app reads USDC on each chain with `erc20BalanceOf(client, usdc, address, blockTag)` at the same policy tag
  (`latest − 3`) as the native balances; it is part of what the buyer pays for. The checker itself doesn't compute
  EVM balances (unchanged).

## 9. What was left out, and why

- **BIP-322 (Bitcoin message signing): skipped.** It signs the BIP143 sighash of a virtual `to_sign` transaction that
  spends a virtual `to_spend` output whose script is the address being proved. The contract doesn't know the token's
  BTC script on-chain (the derived key is off-chain by design, kb/30 §Rec P1), so the caller would supply it and the
  record couldn't bind which address was proved. It would also need a second virtual-transaction builder in the frozen
  contract, a third-party reference implementation for the shared vectors (none is in the lockfile), and wallet
  support on testnet4 is thin. EIP-191 and Solana off-chain cover "prove you control this address" for two of the
  three chains.
- **EIP-712, `eth_sign`, raw hashes:** refused for good (§3.3).
- **Other tokens, SPL tokens, other calldata:** out of scope (feature-ideas "Out of scope").
