# C5: spending allowance (delegated signer)

> **Status:** interface spec, 2026-10-29 (agent contract-allowance, branch `feat/contract-allowance`).
> **Fixed by:** `plan/progress/feature-sprint.md` §Interface decisions, C5. Phase-2 UI work builds against this file.
> **Code:** `contracts/satchel/src/allowance.rs` (state, methods, views, events, spend accounting);
> TS mirror `packages/core/src/policy/allowance.ts` (debits, window, remaining) and `packages/core/src/near/allowance.ts`
> (call builders). Shared vectors: `vectors/allowance.json`.

The owner of a Satchel lets another NEAR account (the **delegate**: a family member, a bot, an AI agent) call
`sign_for` on that token, up to a cap per asset per rolling 24 h. The contract enforces the cap from the amounts it
parses itself, so a delegate can never sign more than its budget, and every delegated signature is a normal record in
the token's clean history (recorded before the MPC call, `requester` = the delegate).

## 1. Methods

All amounts are `U128` decimal strings; times are block-timestamp milliseconds (`u64` JSON numbers).

```rust
/// Owner only. Creates or replaces the allowance of `delegate` on `token_id`.
/// Deposit: ≥ the measured storage, at least 1 yocto (house charging pattern, spec §5.4); the excess is refunded.
#[payable] pub fn set_allowance(&mut self, token_id: TokenId, delegate: AccountId, caps: Vec<CapInput>, expires_at_ms: Option<u64>);

/// Owner only. EXACTLY 1 yocto (like `delist`, S-03). Removes the allowance. Freed storage stays in the contract.
#[payable] pub fn revoke_allowance(&mut self, token_id: TokenId, delegate: AccountId);

// views
pub fn allowances_of(&self, token_id: TokenId) -> Vec<AllowanceView>;               // at most MAX_DELEGATES (4)
pub fn allowance(&self, token_id: TokenId, delegate: AccountId) -> Option<AllowanceView>;
```

`sign_for(token_id, request, mpc_deposit)` keeps its signature. Its caller may now be the owner **or** a delegate with
a live allowance. Nothing else changes for owners.

| Method | Attach (callers) | Notes |
|---|---|---|
| `set_allowance` | **0.01 NEAR**, 30 Tgas | the entry is ≈ 150–900 B (≤ 0.009 NEAR); excess refunded. `ALLOWANCE_ATTACH.set` / `setAllowanceCall` in `@satchel/core/near` |
| `revoke_allowance` | **exactly 1 yocto**, 30 Tgas | `ALLOWANCE_ATTACH.revoke` / `revokeAllowanceCall` |
| `sign_for` (delegate) | as for owners: `min(300, 60+20n)` Tgas, `0.005 NEAR × n` | the delegate pays the record storage **and** its spend-log entries |

### 1.1 JSON

```jsonc
// set_allowance args
{"token_id":"1","delegate":"bot.alice.testnet",
 "caps":[
   {"asset":"btc","limit":"100000"},                                                   // sats
   {"asset":{"evm":{"chain_id":11155111}},"limit":"10000000000000000"},                // wei
   {"asset":"sol","limit":"500000000"},                                                // lamports
   {"asset":{"erc20":{"chain_id":11155111,"token":"1c7d4b196cb0c7b01d743fbc6116a902379c7238"}},"limit":"5000000"}  // token base units
 ],
 "expires_at_ms":1794000000000}          // optional; omit or null = no expiry
// revoke_allowance args
{"token_id":"1","delegate":"bot.alice.testnet"}
```

`Asset` (externally tagged, snake_case; borsh-stored as is):

| JSON | Meaning | Unit |
|---|---|---|
| `"btc"` | BTC testnet4 | sats |
| `"sol"` | SOL devnet | lamports |
| `{"evm":{"chain_id":N}}` | native ETH on EVM chain N; N must be in the contract's `EVM_CHAIN_IDS` (today 11155111; C3 adds 84532, 421614, 11155420) | wei |
| `{"erc20":{"chain_id":N,"token":"<40 hex>"}}` | an ERC-20 token on chain N (C2). `token` input: optional `0x`, any case; stored and shown as 40 lowercase hex | token base units |

The list form extends to new chains or tokens without a shape change: a new `Asset` variant, or a new chain id in
`EVM_CHAIN_IDS`, is all it takes.

### 1.2 Views

```jsonc
// allowance("1", "bot.alice.testnet")  → AllowanceView | null
{"token_id":"1","delegate":"bot.alice.testnet","owner_id":"alice.testnet",
 "set_at_ms":1793000000000,"expires_at_ms":1794000000000,
 "status":"active",                       // "active" | "paused" (token listed) | "expired"
 "now_ms":1793000500000,                  // block timestamp the remaining amounts were computed at
 "window_ms":86400000,"spends_in_window":2,"max_spends":32,
 "caps":[
   {"asset":"btc","limit":"100000","spent":"41000","remaining":"59000",
    "spends":[{"at_ms":1793000100000,"amount":"41000"}]},          // only spends still inside the window, oldest first
   {"asset":{"evm":{"chain_id":11155111}},"limit":"10000000000000000","spent":"0","remaining":"10000000000000000","spends":[]}
 ]}
// allowances_of("1") → [AllowanceView, …]   (delegate order = insertion order; [] when none)
```

- `spent` = Σ `spends[].amount`; `remaining` = `limit − spent` (saturating at 0).
- `spends` lets a client roll the window forward itself (`allowanceRemaining(view, nowMs)` in core): an entry stops
  counting at `at_ms + window_ms`.
- Allowances of a previous owner never show (§4).

### 1.3 Events (NEP-297, `standard: "satchel"`, `version: "1.0.0"`, emitted after every require)

| event | emitted by | `data` |
|---|---|---|
| `allowance_set` | `set_allowance` | `{token_id, owner_id, delegate_id, caps: [{asset, limit}], expires_at_ms}` |
| `allowance_revoked` | `revoke_allowance` | `{token_id, owner_id, delegate_id}` |
| `allowances_cleared` | `nft_transfer`, `buy`, `ft_on_transfer` (only when the token had allowances) | `{token_id, delegate_ids: [..], reason: "transfer" \| "sale"}` |
| `allowance_spent` | `sign_for` by a delegate | `{token_id, owner_id, delegate_id, first_seq, debits: [{asset, amount}]}` |

`sign_requested` is unchanged: its `owner_id` stays the token owner. The delegate shows as `requester` in every
record it creates (`sig_records`) and as `delegate_id` in `allowance_spent`.

## 2. Preconditions and error codes (checked in the order listed; a refusal panics and changes nothing)

**`set_allowance`**
1. token exists → `ERR_TOKEN_NOT_FOUND`
2. predecessor == owner → `ERR_NOT_OWNER`
3. attached ≥ 1 yocto → `ERR_DEPOSIT` (function-call keys can't attach deposits)
4. `delegate ∉ {owner, current_account_id, mpc, usdc}` → `ERR_ALLOWANCE_DELEGATE`
5. caps: 1–8 entries; each `limit > 0`; no asset twice; EVM/ERC-20 `chain_id ∈ EVM_CHAIN_IDS`; ERC-20 `token` is
   exactly 20 bytes of hex → `ERR_ALLOWANCE_CAPS`
6. `expires_at_ms` is `None` or `> now_ms` → `ERR_ALLOWANCE_EXPIRY`
7. expired allowances of the token are dropped first; then, for a new delegate, the token has < 4 delegates →
   `ERR_ALLOWANCE_LIMIT`
8. write; attached ≥ Δstorage × byte cost (min 1 yocto) → `ERR_DEPOSIT: attach ≥ N yocto`; refund the excess
9. emit `allowance_set`

Replacing an existing allowance keeps its spends that are still inside the window, for every asset that keeps a cap
(raising or re-setting a cap never hands out a fresh budget by accident; revoke + set does, on purpose). Setting an
allowance while the token is listed is allowed: it is paused until delist and cleared by a sale.

**`revoke_allowance`**: token exists → `ERR_TOKEN_NOT_FOUND`; owner → `ERR_NOT_OWNER`; exactly 1 yocto →
`ERR_DEPOSIT: attach exactly 1 yocto`; the delegate has an allowance → `ERR_ALLOWANCE_NOT_FOUND`. Works on expired
allowances (cleanup).

**`sign_for`** (spec §5.8; only step 1 changes, and one step is added between 4b and 5):
1. `authorize_signer(token, predecessor, request)`: token exists → `ERR_TOKEN_NOT_FOUND`. The owner is always
   authorized. Anyone else needs an allowance on this token granted by the **current** owner, else `ERR_NOT_OWNER`
   (unchanged for strangers, INV-01). A delegate may sign only fund-moving request kinds (EVM, BTC, SOL), else
   `ERR_ALLOWANCE_KIND`; and the allowance must not be expired (`now_ms < expires_at_ms`), else `ERR_ALLOWANCE_EXPIRED`.
2. listed → `ERR_FROZEN` (**listing pauses delegated signing too**, INV-13 unchanged). Steps 3, 4 and 4b unchanged.
4c. delegates only, `debit_allowance`: compute the request's debits (§3); for each debit: the allowance has a cap for
   that asset → `ERR_ALLOWANCE_ASSET`; `spent_in_window + amount ≤ limit` → `ERR_ALLOWANCE_EXCEEDED: <asset> remaining
   R, request needs A`; the window holds ≤ 32 debits after this request → `ERR_ALLOWANCE_RATE`. Then append one spend
   entry per debit (inside the storage measurement of step 5, so the delegate pays for it).
5.–8. unchanged, except `requester` = the predecessor (owner or delegate). Delegates also get `allowance_spent`
   after `sign_requested`.

| Code | Raised by | Meaning |
|---|---|---|
| `ERR_ALLOWANCE_DELEGATE` | set_allowance | the delegate is the owner, the contract, the MPC or the configured USDC |
| `ERR_ALLOWANCE_CAPS` | set_allowance | caps empty, > 8, duplicate asset, zero limit, chain id not allowed, bad token hex |
| `ERR_ALLOWANCE_EXPIRY` | set_allowance | `expires_at_ms` not in the future |
| `ERR_ALLOWANCE_LIMIT` | set_allowance | the token already has 4 live delegates |
| `ERR_ALLOWANCE_NOT_FOUND` | revoke_allowance | no allowance for that delegate |
| `ERR_ALLOWANCE_EXPIRED` | sign_for | the delegate's allowance has expired |
| `ERR_ALLOWANCE_KIND` | sign_for | a request kind delegates may not sign: message signing (C7), or EVM calldata other than an ERC-20 `transfer` |
| `ERR_ALLOWANCE_ASSET` | sign_for | the request spends an asset the allowance has no cap for |
| `ERR_ALLOWANCE_EXCEEDED` | sign_for | over the remaining amount in the current window (also any amount that overflows u128) |
| `ERR_ALLOWANCE_RATE` | sign_for | more than 32 delegated debits inside one 24 h window |

A delegate calling any other state-changing method is refused by that method's existing owner check:
`list`, `delist`, `nft_transfer`, `set_allowance`, `revoke_allowance` → `ERR_NOT_OWNER`. `withdraw_proceeds` pays only
the caller's own proceeds, and `buy` is an ordinary purchase with the delegate's own money (and `ERR_SELF_BUY` never
applies, since the delegate is not the seller). A delegate has no owner powers.

## 3. What a request spends (debits)

Computed by the contract from the bytes it classified (never from client-supplied amounts), and mirrored exactly by
`allowanceDebits` in core. Every debit is the **worst case** the signature can take out of the Satchel, fees included:

| Request | Debits |
|---|---|
| EVM, `data` empty | `{evm:{chain_id}}`: `value + gas_limit × max_fee_per_gas` |
| EVM, `data` = ERC-20 `transfer(address,uint256)` (selector `a9059cbb`, 68 bytes) (C2) | `{erc20:{chain_id, token: to}}`: the uint256 amount; **and** `{evm:{chain_id}}`: `value + gas_limit × max_fee_per_gas` (the gas is paid in ETH) |
| EVM, any other `data` | refused for delegates, `ERR_ALLOWANCE_KIND` (fail closed, whatever the classifier accepts) |
| BTC | `"btc"`: Σ outputs whose script is not `0014‖pkh` + max(0, Σ input amounts − Σ outputs). `pkh` is the scriptCode pkh of the preimages, which a usable signature must carry (a wrong pkh only yields a signature that can't spend anything, spec §5.9); change back to that P2WPKH doesn't count, the fee does |
| SOL | `"sol"`: `lamports + 5000` (the message has exactly one signature; the classifier refuses compute-budget instructions, so the fee is fixed) |
| message signing (C7), any future kind | refused for delegates, `ERR_ALLOWANCE_KIND` |

- Arithmetic is checked u128. An overflow (e.g. a 16-byte `max_fee` × a large `gas_limit`, or an ERC-20 amount ≥ 2^128)
  refuses the request with `ERR_ALLOWANCE_EXCEEDED`; it is never wrapped or truncated.
- A debit of 0 still needs a cap for its asset (the cap list is also the delegate's chain permission list) and still
  takes a spend entry, so the rate limit counts every delegated request.
- Why fees count: the brief's "EVM: value" alone would let a delegate empty the account with `value = 0` and a huge
  priority fee (the tip goes to the block builder). The BTC fee is likewise unbounded by the outputs alone. The UI
  shows the debit up front ("Uses up to 0.00042 ETH of today's 0.01 ETH"), and real sends spend less.
- Retries (same EVM nonce or BTC inputs) debit again. At most one of them can confirm, so this over-counts, which is
  the safe direction. The owner can re-set the allowance to restore the budget.

## 4. Rules

**Window rule (rolling 24 h, block time).** Each delegated debit is stored as `(at_ms = env::block_timestamp_ms(),
amount)` on its cap. At time `now_ms` an entry counts iff `now_ms < at_ms + 86_400_000`. Entries that no longer count
are pruned whenever the allowance is touched. For every asset and every instant `t`, the debits stamped in
`(t − 24 h, t]` therefore never sum to more than the cap. This is a true sliding window, not a daily reset: there is no
boundary where 2× the cap can be spent. At most 32 entries (`MAX_SPENDS`) can be inside a window, which bounds both the
storage and the number of delegated signatures per day.

**Expiry rule.** An allowance with `expires_at_ms = T` authorizes `sign_for` iff `now_ms < T`. Expired allowances stay
in state (they show as `"expired"`) until the owner revokes or re-sets them, or a `set_allowance` drops them.

**Reset rule.** Every ownership change clears **all** allowances of the token, atomically, in the same receipt:
`nft_transfer`, and the sale paths `buy` and `ft_on_transfer` (through `execute_sale`, which C4's `accept_offer` must
also use). The clear removes the token's entry from state (it doesn't leak storage; the freed stake stays in the
contract, like delist and sale). As a backstop, each token's allowance set records the owner who granted it, and
every read ignores a set whose owner is not the current owner, so a future ownership path that forgot to clear would
still fail closed (except for a token that came back to the same owner).

**Pause rule.** While the token is listed, `sign_for` refuses everyone with `ERR_FROZEN`, delegates included; views
show `"paused"`. After `delist`, delegated signing resumes with the same budget.

**Clean history.** Unchanged. A delegated signature is recorded inside `sign_for` before the MPC call, exactly like an
owner's, so the checker and the Buy gate need nothing new. The quiet period (`last_sign_height`) also counts delegated
signatures.

## 7. Security notes

- **Clean history is untouched.** A delegated signature takes the same path as an owner's: classify, record (before
  the MPC call), charge, emit, fan out. The buyer's checker needs nothing new; delegated records simply name another
  `requester`.
- **Fail closed on unknown kinds.** `authorize_signer` matches `SignRequest` exhaustively and `request_debits` matches
  `SigDetail` exhaustively. A new kind (C7 messages) does not compile until it is decided, and the rule for anything
  whose value can't be capped is `ERR_ALLOWANCE_KIND`. EVM calldata other than a 68-byte ERC-20 `transfer` is refused
  for delegates whatever the classifier accepts.
- **Message signing (C7) is disallowed for delegates**, rather than "capped at count 0", because a refusal at
  authorization can't be misconfigured by a cap list, and a log-in signature by the Satchel key authorizes actions no
  amount cap can measure.
- **Worst-case amounts, fees included** (§3), with checked u128 arithmetic: a delegate can't drain through EVM tips,
  BTC fees or overflow.
- **Griefing a token's history.** A delegate can sign and never broadcast, which leaves `unused` records that block a
  sale until the owner settles them (every record is rebuildable and broadcastable from the event log, §7.6). The
  nonce-gap rule bounds EVM poison, BTC foreign outpoints are non-blocking (S-07), SOL records expire in ≈ 36 s, and the
  32-debit window caps the volume. Owners should grant allowances only to accounts they trust that much, and the UI
  says so.
- **Storage.** The owner pays for the allowance entry, and the delegate pays for its records and spend entries (both
  inside the charged measurement). Every structure is bounded: 4 delegates × 8 caps, and at most 32 live spend entries
  per allowance (pruned on every write). The clear on transfer and sale removes the entry, so no state is stranded.
- **Reset.** An explicit clear on every ownership path (`nft_transfer`, `execute_sale`), plus the owner binding as a
  backstop that fails closed if a future path forgets the clear.

## 8. Merge notes (for the orchestrator)

- **contract-sign (C1, C2, C3, C7).**
  - C3 chain ids: nothing to do. Caps and debits read `EVM_CHAIN_IDS`; add the TS `ALLOWANCE_EVM_CHAIN_IDS` (or pass
    `config().evm_chain_ids` to `validateCaps`).
  - C2 ERC-20: `evm_debits` already handles `transfer(address,uint256)`. Once the classifier accepts it, add one
    `debits` vector (today it sits in `evm_raw`).
  - C7 messages: both exhaustive matches stop compiling. Add the new variant to the "refused" arm of
    `authorize_signer` (`ERR_ALLOWANCE_KIND`), and to `request_debits` as `Err(kind_refusal())`.
  - C1 `history_digest`: unaffected. `requester` is an immutable record field and is part of what it hashes.
- **contract-market (C4, C6).** Any new ownership-change path must call `self.clear_allowances(&token_id, "sale")`. C4
  `accept_offer` should go through `execute_sale`, which already does. C6 withdrawals are owner-only methods; leave
  them unreachable for delegates (a plain `predecessor == owner` check does that).
- **`StorageKey::Allowances`** is appended after `Proceeds`; keep it in the merged order, appended after existing keys.
- **`sign.rs`** changes are three insertions: step 1 (`authorize_signer`), step 4c (`debit_allowance`), and the
  `requester` field plus the `allowance_spent` emit.
