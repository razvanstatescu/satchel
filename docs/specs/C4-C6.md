# C4 + C6: offers, and NEAR-side assets inside a Satchel

> **Status:** interface spec, 2026-10-29 (agent contract-market, branch `feat/contract-market`).
> **Fixed by:** `plan/progress/feature-sprint.md` §Interface decisions, C4 and C6. Phase-2 UI work builds against this file.
> **Code:** `contracts/satchel/src/market.rs` (shared state, FT allowlist, storage credit, totals),
> `contracts/satchel/src/inside.rs` (C6), `contracts/satchel/src/offers.rs` (C4); the `ft_on_transfer` dispatch is in
> `sale.rs`. TS call builders and view types: `packages/core/src/near/market.ts` (`@satchel/core/near`).

**C6.** A Satchel also holds NEAR and allowlisted NEP-141 tokens **inside the contract**, keyed by token id. They belong
to the token, so they move with every ownership change (`nft_transfer`, `buy`, `ft_on_transfer` buy, `accept_offer`)
with no extra step and no clean history: the contract itself enforces who may withdraw. Anyone can deposit; only the
owner can withdraw, never while the token is listed, and every withdrawal bumps the token's `inside_epoch`.

**C4.** Anyone can escrow an **offer** (NEAR or USDC) on any Satchel, listed or not. The offer is bound to the token's
`sig_count` and `inside_epoch` at the time it is made. The owner accepts it (the NFT moves, the seller is paid through
the existing payout + proceeds path), or the offerer cancels it, or anyone cancels it after expiry. The refund always
goes to the offerer.

All amounts are `U128` decimal strings. Times are block-timestamp **milliseconds** (`u64` JSON numbers). Heights are
block heights. Ids (`offer_id`) are `u64` JSON numbers, sequential from 1, never reused.

## 1. Methods

```rust
// ── C6: inside assets ───────────────────────────────────────────────────────────────────────
/// Anyone. Credits `attached − storage` yoctoNEAR to the token. Storage is charged from the deposit itself (house
/// pattern, spec §5.4): only the token's first inside record costs anything (≈ 0.0009 NEAR). Returns the credited amount.
#[payable] pub fn deposit_near(&mut self, token_id: TokenId) -> U128;

/// Owner only, EXACTLY 1 yocto. Refused while listed. Debits first, bumps `inside_epoch`, then transfers
/// `amount` to `receiver_id` (default: the owner), which is never this contract, the MPC or the USDC contract
/// (`ERR_BAD_RECEIVER`, Q-03). A failed transfer is re-credited to the token by the callback.
/// The tx result is the callback's `bool` (true = delivered, false = re-credited).
#[payable] pub fn withdraw_near(&mut self, token_id: TokenId, amount: U128, receiver_id: Option<AccountId>);

/// Same for an allowlisted NEP-141 `ft`: `ft.ft_transfer(receiver_id, amount)` with 1 yocto and 15 Tgas; same
/// receiver rule.
/// A failed `ft_transfer` (e.g. an unregistered receiver) is re-credited to the token.
#[payable] pub fn withdraw_ft(&mut self, token_id: TokenId, ft: AccountId, amount: U128, receiver_id: Option<AccountId>);

/// Self only. MUST NOT panic. No-op (log only; returns false) unless there is exactly one promise result (as S-13).
/// Re-credits the token if the transfer failed, overwriting slots that already exist (no new storage, as S-01).
#[private] pub fn on_inside_withdraw(&mut self, token_id: TokenId, ft: Option<AccountId>, amount: U128) -> bool;

// ── storage credit (pays storage inside `ft_on_transfer`, which carries no NEAR) ─────────────
/// Anyone, payable. Credits `attached − storage` to `account_id` (default: the caller), which is never this
/// contract, the MPC or the USDC contract (`ERR_BAD_RECEIVER`, Q-03: only that account could withdraw the credit).
/// Only the first prepay costs storage (≈ 0.0009 NEAR for the credit slot). Returns the new credit.
#[payable] pub fn prepay_storage(&mut self, account_id: Option<AccountId>) -> U128;
/// EXACTLY 1 yocto. Pays out the caller's whole unused credit (plain transfer; the slot is kept at 0).
#[payable] pub fn withdraw_storage_credit(&mut self);

// ── C4: offers ──────────────────────────────────────────────────────────────────────────────
/// Anyone but the owner. NEAR offer of exactly `amount`: attach `amount + storage` (≈ 0.004 NEAR; attach 0.01 NEAR
/// extra, the excess is refunded). The expected values must equal the token's current ones. Returns the offer id.
#[payable] pub fn make_offer(&mut self, token_id: TokenId, amount: U128, expected_sig_count: u64,
                             expected_inside_epoch: u64, expires_at_ms: u64) -> u64;
/// The offerer at any time, or anyone once `block_timestamp_ms ≥ expires_at_ms`. EXACTLY 1 yocto.
/// Refunds the offerer through the payout path (a failed refund is credited to `proceeds_of(offerer)`).
#[payable] pub fn cancel_offer(&mut self, offer_id: u64);
/// Owner only, EXACTLY 1 yocto. Delists the token if listed, moves the NFT to the offerer, pays the seller
/// (detached payout; a failed payout is credited to `proceeds_of(seller)`).
#[payable] pub fn accept_offer(&mut self, offer_id: u64);

// ── views ───────────────────────────────────────────────────────────────────────────────────
pub fn inside_of(&self, token_id: TokenId) -> Option<InsideView>;          // None = no such token
pub fn storage_credit_of(&self, account_id: AccountId) -> U128;
pub fn offer(&self, offer_id: u64) -> Option<OfferView>;
pub fn offers_for(&self, token_id: TokenId, from_index: u64, limit: u32) -> Vec<OfferView>;     // limit ≤ 50
pub fn offers_by(&self, account_id: AccountId, from_index: u64, limit: u32) -> Vec<OfferView>;  // limit ≤ 50
pub fn market_config(&self) -> MarketConfigView;
pub fn market_totals(&self) -> MarketTotalsView;                         // incl. proceeds_near, escrow_near (M-01)
```

`make_offer` takes an explicit `amount` (the tracker's sketch had none): an offer price must be exact, and the attached
deposit also has to pay the offer's storage. `deposit_near` keeps the sketch's signature: a top-up is credited
`attached − storage`, and storage is only charged on the token's first inside record.

### 1.1 Attachments (callers; `ATTACH_MARKET` in `@satchel/core/near`)

| Call | Gas | Deposit |
|---|---|---|
| `deposit_near` | 30 Tgas | the amount; ≈ 0.0009 NEAR of it pays storage on the token's first inside record |
| `withdraw_near` / `withdraw_ft` | 50 Tgas | exactly 1 yocto |
| `prepay_storage` | 30 Tgas | 0.01 NEAR covers about two USDC offers or two first FT deposits |
| `withdraw_storage_credit` | 30 Tgas | exactly 1 yocto |
| `make_offer` (NEAR) | 30 Tgas | `amount + 0.01 NEAR` (the storage is ≈ 0.003–0.005 NEAR; the excess is refunded) |
| `cancel_offer` / `accept_offer` | 50 Tgas | exactly 1 yocto |
| `ft.ft_transfer_call` (deposit / USDC offer) | 150 Tgas | 1 yocto (to the FT contract) |

### 1.2 `ft_on_transfer` messages

`ft_on_transfer(sender_id, amount, msg)` accepts three messages. The existing buy message is unchanged.

```jsonc
// USDC buy of a listing (unchanged; from the configured USDC only)
{"buy":{"token_id":"3","listing_id":7,"expected_sig_count":4}}
// deposit into a Satchel (from any allowlisted FT: the configured USDC, or wrap.testnet)
{"deposit":"3"}
// USDC offer (from the configured USDC only; sender_id is the offerer)
{"offer":{"token_id":"3","expected_sig_count":4,"expected_inside_epoch":0,"expires_at_ms":1793000000000}}
```

Rules (checked in this order; every refusal **panics**, so the FT refunds 100 %, as for buys):
1. `predecessor ∈ allowlist` → else `ERR_WRONG_TOKEN` (a direct call by an account, or a non-allowlisted FT).
2. `msg` parses as **exactly** one of the three shapes → else `ERR_BAD_MSG`. Parsing is strict (Q-04,
   `#[serde(deny_unknown_fields)]` on `FtMsg` and `OfferMsg`): an unknown field inside `buy` or `offer`, a second
   top-level key, a duplicate field, a missing field, a wrong type or case, the bare JSON `null`, `{}` and `""` are
   all refused. Field order and whitespace are free. A new binding field (`receiver_id`, `max_price`, …) therefore
   needs a new contract; an old contract refuses it instead of ignoring it.
3. `buy` and `offer` additionally need `predecessor == usdc` → else `ERR_WRONG_TOKEN` (wNEAR can be deposited but
   cannot buy or offer).
4. Then the method-specific checks (buy: spec §5.7; deposit: §2.1; offer: §3.1). Success returns `"0"` (all used).

**Storage inside `ft_on_transfer`** is charged from the sender's **storage credit** (`prepay_storage`):
- `deposit`: only when it creates a slot (the token's first deposit of that FT, and the token's inside record if it
  has none). Topping up an existing slot needs no credit.
- `offer`: always (the offer record, its two index entries and the refund slot).
- If the credit is short: `ERR_STORAGE_CREDIT: prepay_storage ≥ N yocto`, a full refund.

## 2. C6 semantics

### 2.1 Deposits
- `deposit_near`: token exists → `ERR_TOKEN_NOT_FOUND`; `attached > storage` → `ERR_DEPOSIT`. Creates the token's
  inside record on the first deposit. Allowed in every state, including while listed (deposits only add).
- FT `deposit`: the token exists → `ERR_TOKEN_NOT_FOUND`; the slot rules in §1.2. The FT slot `(token, ft)` and the
  token's inside record are created on the first deposit; both are kept forever (a later re-credit only overwrites).

### 2.2 Withdrawals (`withdraw_near`, `withdraw_ft`), checked in order
1. token exists → `ERR_TOKEN_NOT_FOUND`;
2. predecessor == owner → `ERR_NOT_OWNER`;
3. exactly 1 yocto → `ERR_DEPOSIT: attach exactly 1 yocto`;
4. not listed → `ERR_LISTED`;
5. (`withdraw_ft`) `ft` is allowlisted → `ERR_WRONG_TOKEN`;
6. `amount > 0` → `ERR_AMOUNT`;
7. `amount ≤ balance` → `ERR_INSIDE_BALANCE`;
8. `receiver_id` (default: the owner) is not this contract, the MPC or the USDC contract → `ERR_BAD_RECEIVER`. This
   is `ensure_receiver`, the set `nft_mint` and `nft_transfer` refuse (Q-03, 2026-10-31; before, only the contract
   itself was refused, and NEAR sent to the MPC or USDC was lost). `prepay_storage(account_id)` applies the same rule.

Effects, in one receipt: debit the balance (the slot stays, at 0 if emptied), `inside_epoch += 1`, the event
`inside_withdraw`, then the transfer `.then(on_inside_withdraw)`, returned with `promise_return`.
`on_inside_withdraw` re-credits the same token by exactly `amount` if the transfer failed. The epoch stays bumped.

**Why withdrawals are blocked while listed.** A buyer is bound to `(listing_id, sig_count)`, not to the inside
balances. With withdrawals frozen, a listed Satchel's inside balances can only grow (deposits, re-credits), so what the
buyer saw is a lower bound of what they get.

### 2.3 FT allowlist
`[usdc (the init arg, if set), "wrap.testnet"]`, compiled in (`market::WNEAR`, shown by `market_config().inside_fts`).
wNEAR on testnet is `wrap.testnet` (checked read-only on 2026-10-29: `ft_metadata` = wNEAR, 24 decimals; storage
0.00125 NEAR). Both are standard NEP-141, and the contract trusts them the same way it trusts USDC for sales: a
malicious upgrade of either could fake deposits of its own token, but it could never touch NEAR or the other token.
**Ops:** the Satchel contract must be storage-registered with each FT before it can receive deposits
(`wrap.testnet.storage_deposit({account_id: <satchel>})`, 0.00125 NEAR; anyone may pay it). Withdrawing to an
unregistered receiver fails and is re-credited; the UI should check `storage_balance_of(receiver)` first.

### 2.4 Contract-paid storage never comes out of escrow (M-01)

**The problem (sprint review M-01).** Three ownership paths take no deposit for storage: `nft_transfer` (NEP-171:
exactly 1 yocto), `buy` (exactly the price) and `accept_offer` (exactly 1 yocto), plus the USDC `buy` inside
`ft_on_transfer`, which carries no NEAR at all. A first-time holder's per-owner set costs the contract 150–250 B (the
S-02 class; measured +150 B to `dave.test.near`, +250 B to a 64-char id; a NEAR buy by a 64-char holder that also
frees the listing is still +63 B). Before C4/C6 that came out of the contract's own NEAR. Since C4/C6 the same
balance also holds user escrow, so once the contract's own surplus was gone those calls silently spent inside NEAR,
offers, credit or proceeds, and the last `withdraw_near` failed with `LackBalanceForState`.

**The rule.** The contract's own NEAR (birth funding, freed stake, gas rewards) is the only buffer for that storage.
`ensure_solvent(s0)` runs **last** in `nft_transfer`, `execute_sale` (NEAR and USDC buy) and `accept_offer`, after
the payout transfer has been created, so the price or offer amount is already deducted from `env::account_balance()`.
It flushes every cached collection, and if the call **grew** storage (`storage_usage > s0`) it requires

    balance ≥ storage_usage × byte_cost + escrow_near,   escrow_near = Σ inside.near + Σ open NEAR offers + Σ storage credit + Σ proceeds(near)

or panics `ERR_INSOLVENT: top the contract up by ≥ N yocto (a plain transfer); its own NEAR pays storage, never
escrow` (with no escrow at all, a short buffer gets this stable code too, instead of the runtime's
`LackBalanceForState`). The receipt rolls back: the NFT doesn't move, a NEAR buyer gets the price back, a USDC buy is refunded
100 % by the FT. A call that frees or keeps its storage never fails here (it can't make I-M1 worse), so an accept,
which frees the offer record (measured −194 B and −143 B net), is never blocked by a short buffer. Anyone can refill the
buffer with a plain transfer to the contract; the monitor alerts on the spare NEAR (`free − escrow_near`, §4).

**Every path that changes storage, reviewed:** `nft_mint`, `list`, `sign_for` (records, C3 nonce slots, C5 spend
entries), `set_allowance`, `deposit_near`, `prepay_storage` and `make_offer` charge the caller exactly (`charge_storage`);
`ft_deposit` and the USDC offer charge the sender's storage credit (`charge_credit`), which moves NEAR from
`storage_credit` to stake one-for-one; `delist`, `revoke_allowance` and `cancel_offer` only free storage; the
callbacks (`on_signed`, `on_payout`, `on_inside_withdraw`) and the withdrawals (`withdraw_near`, `withdraw_ft`,
`withdraw_proceeds`, `withdraw_storage_credit`) only overwrite fixed-size slots that already exist (I-M6). So the three
guarded paths are the only contract-paid growth.

**Why not caller-pays.** Charging the measured delta to the caller, as `nft_mint` does, would break the interfaces:
wallets and marketplaces attach exactly 1 yocto to `nft_transfer` (NEP-171 requires it), `buy` is bound to the exact
price (`ERR_WRONG_AMOUNT`), and a USDC buy carries no NEAR, so it would need a storage credit the buyer has never
heard of. The guard keeps every interface as it is and turns the worst case from a loss of escrow into a recoverable
refusal of new-holder transfers until someone tops up (a griefer pays ≈ 0.0049 NEAR to drain 0.0025 NEAR of buffer,
review M-01). `nft_transfer` stays NEP-171 compatible.

**Bookkeeping.** `MarketTotals.proceeds_near` is the running Σ `proceeds[(·, near)]`: `on_payout` adds a failed NEAR
payout or refund (saturating; the callback never panics), `withdraw_proceeds(near)` subtracts what it pays out. In the
window between a failed transfer's refund receipt and `on_payout`, the total can briefly lead or lag the balance by that
amount; at rest it is exact (I-M2).

## 3. C4 semantics

### 3.1 `make_offer` (NEAR) and the `offer` FT message (USDC), checked in order
1. token exists → `ERR_TOKEN_NOT_FOUND`;
2. offerer ≠ current owner → `ERR_SELF_BUY`;
3. offerer passes the receiver guard (not this contract, the MPC or the USDC contract) → `ERR_BAD_RECEIVER`;
4. `amount > 0` → `ERR_AMOUNT`;
5. `expected_sig_count == sig_count` and `expected_inside_epoch == inside_epoch` (current values) → `ERR_OFFER_STALE`;
6. `now_ms < expires_at_ms ≤ now_ms + MAX_OFFER_TTL_MS` (90 days) → `ERR_OFFER_EXPIRY`;
7. the offerer has `< MAX_OFFERS_PER_ACCOUNT` (20) open offers → `ERR_TOO_MANY_OFFERS`;
8. NEAR: `attached ≥ amount + storage` → `ERR_DEPOSIT` (excess refunded). USDC: storage credit (§1.2).

Effects: the offer record, its entries in the per-token and per-offerer indexes, and the offerer's proceeds slot
`(offerer, currency)` if absent (so a failed refund only overwrites, as S-01), all charged to the offerer. Event
`offer_made`. Offers may be made on listed and unlisted tokens alike.

### 3.2 `accept_offer(offer_id)`, checked in order
1. offer exists → `ERR_NO_OFFER`;
2. predecessor == owner of `offer.token_id` → `ERR_NOT_OWNER`;
3. exactly 1 yocto → `ERR_DEPOSIT`;
4. offerer ≠ owner → `ERR_SELF_BUY`;
5. `now_ms < expires_at_ms` → `ERR_OFFER_EXPIRED`;
6. `sig_count == expected_sig_count` and `inside_epoch == expected_inside_epoch` → `ERR_OFFER_STALE`;
7. the quiet period: `height ≥ listable_at` (`last_sign_height + 250`, or 0 if never signed) → `ERR_QUIET_PERIOD`.

Effects, in **one receipt**:
- if listed: clear the listing, drop it from `listings`, emit `delisted`;
- remove the offer and its index entries;
- `tokens.internal_transfer(owner → offerer, memo "offer")` (standard `nft_transfer` event);
- **`on_owner_change(token_id)`**, the single post-transfer hook that `nft_transfer` and `execute_sale` (buy, USDC buy)
  also call. C5 clears allowances there;
- reserve `proceeds[(seller, currency)] = 0` if absent: the freed offer record pays for it, so the payout re-credit
  never needs contract-paid storage;
- event `offer_accepted`;
- a **detached** payout of `amount` to the seller: NEAR transfer or `usdc.ft_transfer` (the existing `payout` →
  `on_payout`; on failure, `proceeds_of(seller)`);
- last, `ensure_solvent` (§2.4): `ERR_INSOLVENT` if the accept grew storage that only escrow could pay (in practice an
  accept frees more than it adds, so this never bites).

Inside balances move with the token (they are keyed by token id). Other open offers on the token stay open. They are
still bound to the same `sig_count` and `inside_epoch`, so the new owner may accept them, and their offerers may cancel.

### 3.3 `cancel_offer(offer_id)`
offer exists → `ERR_NO_OFFER`; exactly 1 yocto → `ERR_DEPOSIT`; predecessor == offerer, or
`now_ms ≥ expires_at_ms` → `ERR_NOT_OFFERER`. Removes the offer, emits `offer_cancelled`, and returns the refund
promise (`payout(offerer, currency, amount)` → `on_payout`; a failed refund is credited to `proceeds_of(offerer)`,
withdrawable with `withdraw_proceeds`).

### 3.4 What an offer binds to, and what the UI must do
- `sig_count` freezes the clean-history record set: any new signature makes the offer unacceptable.
- `inside_epoch` freezes the inside balances from below: any withdrawal makes the offer unacceptable, and deposits
  only add.
- The quiet period at accept guarantees that no MPC request can still produce a signature (spec §5.7).
- **The offer UI must run the full clean-history check before `make_offer`**, exactly as the Buy gate does. The
  contract cannot judge whether records are dead. A record that is dead stays dead, and the balances on the other
  chains can only move through a new signature, which would change `sig_count`.

### 3.5 Limits
- `MAX_OFFERS_PER_ACCOUNT = 20` open offers per offerer.
- **There is no per-token cap, on purpose.** A per-token cap would let one party fill a token's slots with dust offers
  and block real buyers. Storage can't be griefed instead: each offer's storage is paid by its offerer, and the
  per-token index is O(1) (swap-remove), so accepting or cancelling costs the same gas however many offers a token has.
- `MAX_OFFER_TTL_MS = 7_776_000_000` (90 days).
- Views page with `limit ≤ 50` (`MAX_PAGE`). The indexes use swap-remove, so a removal between page reads can move an
  entry (the same caveat as `listings`, S-12). Re-read `offer(id)` before acting.

## 5. Events (NEP-297, `standard: "satchel"`, `version: "1.0.0"`)

| event | emitted by | `data` |
|---|---|---|
| `inside_deposit` | `deposit_near`, `ft_on_transfer` deposit | `{token_id, sender_id, ft: null \| account, amount}` |
| `inside_withdraw` | `withdraw_near`, `withdraw_ft` | `{token_id, owner_id, receiver_id, ft, amount, inside_epoch}` (the new epoch) |

## 6. Error codes (new; existing codes keep their meaning)

| Code | Raised by | Meaning |
|---|---|---|
| `ERR_AMOUNT` | withdraw_near, withdraw_ft, make_offer, offer msg | amount must be > 0 |
| `ERR_INSIDE_BALANCE` | withdraw_near, withdraw_ft | not that much inside this Satchel |
| `ERR_STORAGE_CREDIT` | ft_on_transfer deposit / offer | the sender's storage credit is short: `prepay_storage` first (the message names the yocto needed) |
| `ERR_NO_OFFER` | accept_offer, cancel_offer | no open offer with that id |
| `ERR_NOT_OFFERER` | cancel_offer | only the offerer may cancel before expiry |
| `ERR_OFFER_EXPIRED` | accept_offer | the offer has expired |
| `ERR_OFFER_EXPIRY` | make_offer, offer msg | `expires_at_ms` must be in the future and at most 90 days away |
| `ERR_OFFER_STALE` | make_offer, offer msg, accept_offer | `sig_count` or `inside_epoch` differs from the offer's |
| `ERR_TOO_MANY_OFFERS` | make_offer, offer msg | the offerer already has 20 open offers |
| `ERR_INSOLVENT` | nft_transfer, buy, ft_on_transfer buy, accept_offer | M-01 (§2.4): the call needs contract-paid storage that only escrow could pay. The detail names the yocto to top up; anyone can top the contract up with a plain transfer, then retry. A USDC buy is refunded 100 % |

Reused: `ERR_TOKEN_NOT_FOUND`, `ERR_NOT_OWNER`, `ERR_DEPOSIT`, `ERR_LISTED` (withdraw while listed), `ERR_BAD_RECEIVER`
(withdraw_near, withdraw_ft, prepay_storage and the offerer: the contract, the MPC or USDC; Q-03),
`ERR_SELF_BUY`, `ERR_QUIET_PERIOD`, `ERR_NOTHING_OWED` (withdraw_storage_credit), `ERR_WRONG_TOKEN`, `ERR_BAD_MSG`
(its sentence now names all three message shapes; also any unknown field in a msg, Q-04).

## 7. Accounting invariants (each is a named test)

| ID | Property | Tests |
|---|---|---|

## 8. State and merge notes
- **One field**, `Contract.market: Market` (`market.rs`), holds all the C4/C6 state, so `lib.rs` changes by one field
  and one constructor line.
- New `StorageKey` variants, **appended after C5's `Allowances`** (main 24a680b, merged into this branch), in this
  order: `Inside`, `InsideFt`, `Offers`, `OffersByToken`, `OffersByTokenLen`, `OffersByAccount`, `OffersByAccountLen`,
  `StorageCredit`. Prefix bytes 9–16.
- `lib.rs` gains `pub(crate) fn on_owner_change(&mut self, token_id: &TokenId, reason: &str)`, the single
  post-transfer hook. It calls C5's `clear_allowances(token_id, reason)` and is called after every ownership change:
  `nft_transfer` ("transfer"), `execute_sale` (buy and USDC buy; "sale") and `accept_offer` ("sale", so C5's
  `allowances_cleared` event keeps its documented `"transfer" | "sale"` vocabulary). C5's direct calls at the first two
  sites were folded into the hook when `main` was merged.
- **Delegates (C5)** have no C4/C6 powers: `withdraw_near`, `withdraw_ft` and `accept_offer` check
  `predecessor == owner` (`ERR_NOT_OWNER`), and `cancel_offer` checks the offerer (`ERR_NOT_OFFERER`). A delegate may
  make an offer with its own money like any account. Tests: unit
  `delegates_cannot_withdraw_or_accept_and_accept_clears_allowances`, sandbox
  `offer_accept_clears_allowances_and_delegates_have_no_market_powers`.
- `sale.rs`: `payout` and `ensure_one_yocto` become `pub(crate)`; `ft_on_transfer` dispatches the three messages.
