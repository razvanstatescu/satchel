# Live proofs: every Satchel action on testnet

> Part of the Satchel docs. Start at the [README](../../README.md); a guide for AI reviewers is in
> [`AGENTS.md`](../../AGENTS.md). The other read-only checks are in [`docs/verify.md`](../verify.md).

Each row below is one real testnet transaction. Most show an action working. Some show the contract refusing
something it must refuse. You can check all of them yourself, read-only, with no wallet and no key:

```sh
tools/proofs.sh            # fetch every transaction and check it: PASS or FAIL per proof, with its explorer link
tools/proofs.sh --print    # list every proof, its links, the curl commands and what must hold (no network)
```

It needs `bash`, `curl` and `python3`, nothing else. It exits non-zero if any proof fails.

The release contract is `satchel.satchelhq.testnet`, born keyless; the same proof set is made there with one command
(`pnpm --filter @satchel/tools e2e:proofs --contract satchel.satchelhq.testnet --send --yes`), and this page then points to it.

Most proofs were made for this page. The ones marked *earlier* are older transactions on the same contract that still prove their point. Each entry in `proofs.json` has its date and block.

## What the checker looks at

For every proof, from the FastNEAR transaction API (it keeps old transactions; the NEAR RPC is the fallback):

- who signed it, which contract and which method it called, and the arguments that matter;
- that it succeeded, or that it failed with the exact error code, and that nothing changed (no event);
- the events the contract logged (NEP-297), such as `sold` with the buyer, the seller and the price.

For a signature, it also redoes the cryptography in plain Python:

- the contract hashed the bytes it recorded itself, so it never signed a hash it could not read;
- the MPC signature verifies against the Satchel's own address: secp256k1 key recovery for EVM and Bitcoin, ed25519
  for Solana.

For a send on another chain, it rebuilds that chain's transaction from the NEAR record. Then it checks that the
transaction exists on Sepolia, Bitcoin testnet4 or Solana devnet, that it comes from the Satchel's address, that the
nonce or the coins spent match the record, and that it is confirmed.

## Still for sale

Two Satchels from these proofs were left listed on `dev2.satchelhq.testnet`. The hosted app reads `satchel.satchelhq.testnet` now, so they are not on its market; `tools/proofs.sh` still checks every transaction above:

- **Satchel #5**, listed for NEAR by its new owner. It was given, signed messages, was sold and signed again, and it holds the ETH, USDC and SOL sent above. Its signatures are all messages, which never block a sale, so its verdict is clean.
- **Satchel #6**, listed for USDC. It has never signed, so its verdict is `empty`, the clean case for a Satchel with no history.

## Not here yet

- **A buy with USDC.** It needs USDC on NEAR testnet, and the only source is Circle's faucet, which a person must
  use in a browser. Satchel #6 stays listed for USDC until then. The fake-payment refusal above already shows that
  only the USDC contract can pay for it. To add the buy: `e2e:proofs --only buy-usdc --merge --send --yes`.
- **A timed-out MPC request.** Testnet MPC requests sometimes time out under load, but none did during this run,
  and a timeout is not forced on purpose. The behaviour is covered by the sandbox tests (`timeout_never_sticks`).

## For machines

[`proofs.json`](proofs.json) holds the same set. Each entry has an `id`, the `action`, what it `shows`, the NEAR `tx`,
`signer`, `receiver`, `method` and `args`, the `expect`ed outcome (`success`, or `failure` with the `error` code),
the `events` that must appear (with the data fields that must match) and the `absent_events` that must not, and for
signatures a `signature` block (chain, kind, MPC path, the address it must verify against) and an `external` block
(the other chain's transaction and its explorer link). `adopted: true` marks an earlier transaction (the *earlier*
rows above). `satchels` lists the addresses of every Satchel involved, and `mpc_timeouts`, when present, the MPC
requests that timed out during the run. The blocks of this page between `proofs:` markers are generated from
`proofs.json` (`pnpm --filter @satchel/tools e2e:proofs --render`).
